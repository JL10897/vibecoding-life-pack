# Coding Agent Notes

这份文件保存编码和交付方面的详细经验。所有 Agent 都应遵循的精简规则以 `AgentPrinciples.md` 为准；这里保留解释、具体做法和项目专项经验。

## 通用编码与交付原则

1. **先确认任务性质和目标**
   - 先说清关键假设、歧义和取舍。不清楚时问，不要默默选择一种解释。
   - 判断任务是一次性处理还是长期能力。一次性工作不要混入长期 pipeline。
   - 把请求转成可检查的完成标准；多步任务先列简短计划。

2. **保持实现简单**
   - 只写解决当前问题所需的最少代码。
   - 不增加未要求的功能、灵活性、抽象层或无关的错误处理。
   - 单次使用的逻辑不为“以后可能复用”提前抽象。

3. **只修改必要内容**
   - 不顺手重构未损坏的代码，不统一无关格式，不改写邻近注释。
   - 只清理由本次改动产生的无用文件、导入或分支；不主动删除原有 dead code。
   - 遵循代码库已有的结构、命名和风格。认为现有做法有害时，先说明，不另起一套模式。

4. **修改前先阅读并保留旧状态**
   - 阅读相关文件、exports、直接调用方、共用工具、测试和项目说明。
   - 先检查 Git 状态，区分已有改动和本次改动。不要覆盖、丢弃或顺带提交不明来源的工作。
   - 确保旧版本可通过已有 commit、备份或其他明确方式恢复。

5. **让模型做判断，让代码做确定性工作**
   - 分类、起草、总结和语义抽取可以交给模型。
   - 路由、重试、计算、校验和确定性转换优先使用代码。

6. **明确处理冲突**
   - 两种规则、数据口径或实现模式冲突时，不要折中拼接。
   - 选择更具体、更新或经过验证的一种，说明理由，并指出另一种留待清理。

7. **测试要验证意图**
   - 测试应说明为什么该行为重要，而不只是复现当前实现。
   - 修改后运行与风险相称的检查；跳过的检查必须明确说明。

8. **分阶段记清状态**
   - 重要步骤完成后，说明改了什么、验证了什么、还剩什么。
   - 无法准确复述当前状态时，暂停并重新梳理。
   - 失败、不确定性和未完成事项要直接说明，不用含糊的“已完成”掩盖。

9. **使用具体、自然的语言**
   - 写清谁在什么情况下做什么、信息写在哪里、哪些内容可以或不能修改、如何检查完成。
   - 除非项目已经明确定义，否则避免抽象工程术语、架构黑话、咨询式表达和不必要的名词化表达。

10. **正文和执行汇报分开**
    - HTML、图表、README 等正文只保留读者理解和使用结果所需的信息。
    - 不在正文里写执行过程、合规说明、自我评价或“没有做什么”之类的防御性表述。
    - 只有影响使用、判断、正确性或安全性的限制、风险和未完成事项才进入正文；其他细节放在状态汇报或 Git 历史中。

## 项目专项经验

以下规则来自标签、画像、报告和部署类项目。只有任务涉及对应工作时才使用，不应作为所有编码任务的默认要求。

### 批处理与输出目录

- 每次运行新批处理或生成任务前，先整理旧输出。把不再作为当前主结果使用的临时预览、旧 batch、viewer 和中间产物移到 `output/archive/`。
- 不删除或覆盖仍在运行的产物。不确定时优先 archive。

### Taxonomy、schema 与完整消费链路

- 修改 taxonomy 或 schema 前，先检查现有字段、槽位、prompt 输出、normalize、aggregate、render、交互下钻、验证脚本和旧数据兼容。
- 新结构必须说明旧字段如何迁移：继承、合并、删除和信息去向都要明确。
- 概念变化必须落到实际输入、归纳和消费链路。没有真实上游字段或下游消费时，不要只在展示层增加节点或箭头。
- 用户讨论产品概念时，要主动把变化翻译成文件级修改清单。

### 标签、画像与证据

- 影响画像、偏好、关系和需求的结论要保存证据文本及必要上下文，例如阶段、子场景、发起方、频次和前后事件。
- Prompt 同时写正例、反例和不过度判断规则。常规动作、被动回应、临时高压反应、ASR 噪音、玩笑和单次情绪不能直接升级成稳定偏好。
- Normalize 不只做枚举 snap，还要处理旧值映射、自由文本收敛、空泛占位、过长解释和新旧 schema fallback。
- 需要频次、分布或行为统计时，先由脚本计算候选统计，再让模型做语义复核。
- 命令成功不代表标签质量正确。要检查聚合摘要、unknown 比例、证据质量和百分比统计单位。

### 端到端验证

- Schema 改造后至少检查编译、linter、normalize 烟测、聚合和渲染；条件允许时用新 schema 重跑样本。
- 前端修改后做 JavaScript 语法检查，并确认关键 DOM、canvas、table、初始化函数和数据字段存在。
- 下钻功能要验证跳转目标、筛选字段和实际筛选结果。
- 验证产物尽量使用独立文件名，确认稳定后再替换默认结果。

### 报告结构与视觉表达

- 同类信息优先使用同构的 DOM、交互和空状态，不靠 CSS 强行补齐结构差异。
- 复用项目已有的视觉语言。分布信息优先用报告图表；pill 更适合筛选状态或小标签。
- 用户总览只放可直接理解的结论和洞察；质检矩阵、字段一致性和 prompt 诊断默认放开发者模式或折叠区，并能下钻到样本。

### 完整版本与性能

- 用户要求 full 版本时，不用轻量版偷换目标。先通过外部化资源、懒加载、拆分数据或修复 JavaScript 错误解决性能问题。
- 只有用户明确同意，才能改变交付内容或降级版本。

### 部署和最终交付面

- 生成文件不等于交付。用户需要在线预览时，要验证真实 URL、服务目录、端口、协议、缓存、HTTP 状态和本次新增内容的 marker。
- 域名和协议不能猜。短域名、完整域名、HTTP 和 HTTPS 需要分别确认。

### 计划的执行粒度

- 不只写“优化 prompt”“增加图表”或“支持下钻”。执行计划要落实到文件、函数、数据聚合、展示形式、交互、空状态和验收方式。
- 下钻计划要定义筛选类型、字段、跳转目标、目标页自动填充方式和异常组合的展示方式。

### 长期要求写回项目

- 新发现的固定要求，例如部署地址、生成方式、性能阈值和验收 marker，要写入对应项目的 README、plan 或 Agent 规则。
- 不要只在对话中约定长期要求。
