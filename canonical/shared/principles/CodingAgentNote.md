
这个文档用来记录之后需要告诉 Coding Agent 的一些写代码规范。我现在先从我想到的讲，之后我们将这个整合一下。

1.  **搞清楚是一次性使用还是长期使用**
    如果搞不清楚，要明确地问用户。如果是一次性使用，尽可能将它剥离出常规使用的 pipeline。

2.  **任何修改前都要确认旧版可以追溯**
    在做修改之前，都要确认是否已经 commit 好，或者说旧的变动是否已经做好保存和修复，以便未来需要修复时能随时恢复。

3.  **文件结构永远保持清晰**
    随时随地想好现在的文件格式属于什么部分，不要把很多东西都扔到一个文件里面。

更新一个功能的时候随时注意在原来的代码块上做还是去新开一个逻辑，不要什么都堆在一起变成屎山。

注意统一命名规则，有对于命名规则不确定的时候要问用户

4.  **每次跑新的批处理/生成任务前，先清理旧输出**
    如果 output 目录里已经有上一次临时预览、旧 batch、旧 prompt preview、过期 viewer 或中间产物，不要继续堆在主目录里。
    先把不再作为当前主结果使用的文件移动到 `output/archive/`，必要时按时间或任务名建子目录，保证当前 output 目录只保留这次要看的关键输入、输出、日志和 review 文件。
    注意不要删除或覆盖仍在运行中的任务产物；如果不确定某个文件是否还需要，优先 archive，不要直接删。

5.  **改 taxonomy / schema 前，先看现有槽位和消费链路**
    不要只从概念上设计一套“更合理的新结构”。先查清楚当前已经有哪些字段、槽位、prompt 输出、归一化逻辑、聚合逻辑和渲染逻辑。
    提新结构时必须写清楚“旧结构如何迁移到新结构”：每个新槽位继承了哪个旧槽位、哪些旧字段被合并、哪些旧字段被删除、旧字段里的信息分别流向哪里。
    尤其是把一个抽象字段拆掉时，要写清楚拆分去向。例如“不再保留风险偏好”时，要说明战斗风险、资源冒险、路径/进圈风险分别并入哪个新槽位。
    只要改 prompt 产出的 schema，就要同步检查整条链路：prompt 怎么产出、schema 字段叫什么、normalize 怎么兜底、aggregate 怎么统计、render 怎么展示、旧数据要不要兼容。
    用户在讨论产品概念时，coding agent 要主动把它翻译成文件级修改清单，不要等到最后才发现下游文件没有跟着改。

6.  **标签/画像类代码要把“证据上下文”作为一等结构**
    不要只让 LLM 输出一个结论字符串。凡是会影响画像、偏好、关系、需求的字段，都要考虑是否需要同步保存证据文本、阶段/子场景、发起方、单次/反复/明确表态、前一句或事件上下文。
    prompt 里要同时写正例和反例，尤其要明确哪些常规动作、被动回应、临时高压反应、ASR 噪音、玩笑/破壁不能直接打成稳定偏好。
    normalize 不能只做枚举 snap；还要处理旧值映射、自由文本收敛、空泛占位降级、过长解释降级，以及新旧 schema 的 fallback。
    如果一个判断需要频次、分布或行为统计，不要只交给 LLM。优先用脚本算候选统计/先验，再让 LLM 做语义复核。

7.  **做完 schema 改造后必须跑端到端验证**
    至少要跑 Python 编译、linter、normalize 烟测、聚合、渲染；有数据和网关时，要用新 schema 重跑一批样本。
    验证时不要只看命令是否成功，还要读聚合摘要：如果出现阶段覆盖全 0、旧字段还在统计、模板字段混入长解释、未知值异常偏高/偏低，都说明链路还有旧逻辑或 normalize 问题。
    生成的新产物如果只是验证用，尽量另起文件名，不要覆盖默认主产物；确认稳定后再决定是否替换默认输出。

8.  **前端同类信息优先同构渲染，不要靠 CSS 强行补齐结构差异**
    如果几个 UI 元素在语义上属于同一组信息，优先让它们使用同一种 DOM 结构、交互结构和状态结构，而不是一个用 `details/summary`、一个用普通 `div`，再靠 margin、padding、line-height 去补视觉差异。
    浏览器默认样式、内置 marker、可点击区域、焦点态、行高和空白占位都可能造成隐性不齐。遇到对齐问题时，先检查结构是否一致，再考虑 CSS 微调。
    没有数据时也要保留同构结构和明确空状态。例如同一组可展开信息里，即使某项没有明细，也应该展示“无数据/无事件/暂无记录”之类的空内容，而不是直接少一个可展开区域。
    这样用户看到的是稳定的信息模型：每一行都能点击、都能展开、都有结果；区别只在内容多少，而不是布局和交互突然变化。

9.  **生成文件不等于交付，真实地址能打开才算完成**
    报告类任务不能停在“已经生成 `deploy/index.html`”。如果用户需要 anydev/devcloud 预览，就必须确认服务目录、端口、域名和协议都正确。
    验证时至少检查：目标 URL 返回 `HTTP 200`、服务进程 cwd 指向当前项目 `deploy/`、页面 HTML 包含本次新增模块的 marker、外部资源能访问。
    遇到域名问题不要猜。必须确认完整域名、后缀、端口和协议，例如短域名和带 `.woa.com` 的完整域名可能完全不同；HTTP server 被 HTTPS 访问会在日志里出现 400，不代表页面坏了。

10. **用户要 full 版本时，不要用轻量版替代**
    性能问题要优先通过工程手段解决，而不是删内容。比如单文件 HTML 太大时，先看体积构成：base64 大图、完整对话、内联 JSON、内联 vendor JS 哪个是大头。
    如果大图是主因，保留 full 内容，把 base64 图片外部化成文件；如果 JS 报错导致只显示标题，要先做 `node --check` 或浏览器错误定位；如果完整对话太重，再考虑懒加载或折叠加载。
    只有用户明确同意，才可以把 full 交付降级成轻量版。

11. **报告 UI 要复用既有视觉语言，不要临时堆筛选 pill**
    如果项目已有成熟报告样式，例如 `TwoDay` 里的 `chart-box + Chart.js`、bar、doughnut、气泡/词云，就优先复用这套表达。
    对“分布”这种汇报信息，默认用图表卡片；pill 更适合筛选状态或小标签，不适合作为主要可视化。
    做 UI 修改时要区分“信息结构”和“CSS 微调”：用户觉得丑，往往是表达形式不对，而不是单纯字号/颜色问题。

12. **改完前端必须做 JS 级验证**
    只跑 Python 编译不够。内联 JS 拼字符串很容易因为引号转义出错，导致页面只剩标题、view 没激活。
    报告 HTML 生成后，应抽取内联 `<script>` 用 `node --check` 检查；如果有图表或下钻，确认 HTML 中存在对应 canvas id、初始化函数和数据字段。
    部署后用 cache-busting query 参数验证新版本，例如 `?v=xxx`，避免浏览器拿旧缓存。

13. **schema 改造后要看聚合摘要是否符合产品口径**
    命令成功不代表标签质量正确。比如基础画像严格 unknown 的口径下，如果年龄、性别、粉丝倾向突然大量非未知，就要抽查 evidence，必要时在 prompt 和 normalize 加硬闸门。
    聚合摘要中的百分比也要看单位：按样本数统计和按事件次数统计不能混用，否则会出现超过 100% 的误导性输出。

14. **长期执行要求要写回项目目录**
    如果一次协作中发现新的固定要求，例如 anydev 部署地址、full 版本 external-assets 生成方式、性能阈值、验收 marker，要写回项目目录的 plan 或 README。
    不能只在对话里说清楚，否则下一轮 agent 很容易忘记。

15. **概念变化必须落到整条代码链路**
    用户讨论的字段、taxonomy、prompt 口径、信息层级变化，不能只停留在概念层或 render 层。Coding Agent 要主动检查并同步：输入数据、prompt 输出、schema/normalize、aggregate、render、交互下钻、验证脚本和部署产物。
    如果某个 UI 节点、图表层级或信息流向没有真实上游字段、归纳逻辑或下游消费，就不要只在前端画出来。展示层不能伪造推理层。

16. **计划必须写到文件、函数和交互级**
    不要只写“优化 prompt”“增加图表”“支持下钻”。执行计划至少要说明：改哪个文件、加哪个 helper 或函数、数据如何聚合、图表用什么形式、颜色怎么定、DOM/Chart.js/HTML table 怎么实现、空状态怎么处理、点击后如何筛选和跳转、如何验收。
    如果图表能下钻，必须定义 filter kind、筛选字段、跳转目标、样本页如何自动填筛选条件，以及异常组合如何展示。

17. **不要只改展示，不改来源**
    如果报告里新增一个中间层、证据层或聚合结论，先确认 prompt 和数据结构真的产出它，normalize 不会丢失它，aggregate 能统计它，render 能展示它，逐样本页能回到证据。
    任何“信息流向图”都要和真实执行链路一致：箭头表示下游确实消费上游信息，而不是视觉上有关联。

18. **开发者诊断和用户汇报要分层**
    质检矩阵、异常组合、覆盖率、字段一致性验证、prompt 诊断图，默认放开发者模式或折叠区；普通总览只放用户能直接理解的主结论和核心洞察。
    不要把内部验证图包装成产品结论。开发者图也要能下钻到样本，方便确认是不是打标错误、数据稀疏，还是规则本身合理。

19. **验证要覆盖最终交付面**
    命令成功不等于交付完成。除 Python 编译和脚本运行外，还要验证生成页面能打开、JS 语法通过、关键 DOM/canvas/table id 存在、图表初始化数据存在、点击下钻能跳到逐样本并筛出正确样本。
    如果涉及部署，必须验证真实 URL、服务目录、端口、协议、缓存和本次新增 marker。用户要的是可访问的结果，不是本地文件路径。
