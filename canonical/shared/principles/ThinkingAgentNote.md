# Thinking Agent Notes

## Taxonomy 调整时的抽象判断逻辑

1. 先问“这个信息回答什么问题”

不要一听到新反馈就新增维度。先判断它是在回答一个全新的问题，还是把已有问题说得更具体。只有当它回答的问题无法被现有槽位稳定承载时，才考虑新增槽位。

2. 每个槽位只回答一个稳定问题

一个槽位最好有清晰的主问题，避免多个维度都在写同一件事。判断时可以用一句话测试：这个槽位到底是在写“态度”“表达方式”“行为结果”“资源需求”，还是“协作边界”？

3. 先划边界，再定枚举

不要先急着设计几档。先确定这个信息的性质、归属和排除项，再定枚举。边界不清时，枚举会看似完整但互相重叠，后续 prompt 也容易漂。

4. 拆分标准是“是否并列、是否可独立观察”

如果两个信息回答不同问题、证据来源不同、可以独立观察，就适合拆成平行小槽位。如果只是同一问题的不同描述，就不要拆太细，避免 action space 过大。

5. 抽象概念要落回可观察信号

不要追求概念听起来高级。一个好槽位应该能被样本证据支撑，能被 prompt 稳定抽取，能被下游策略使用。抽象词如果容易和多个维度混在一起，就要改成更具体、可观察的说法。

6. 新结构必须说明旧结构如何迁移

讨论 taxonomy 不是只讨论理想结构，还要同步问：现有槽位有哪些？新槽位继承了谁？哪些旧字段被合并或删除？被拆掉的信息分别流向哪里？否则方案容易看起来像重写，而不是基于现有系统演进。

7. 粒度服务于行动，不服务于完整性

槽位不是越细越好。细分只有在它能改变后续判断或策略时才有价值。如果细分后不能带来更稳定的 prompt 输出或更明确的行动差异，就应该合并或作为备注处理。

8. 先设计证据抓手，再设计结论名

不要先被一个好听的结论名带着走。先问：什么样的原话、行为、上下文、频次或反例能稳定支持这个结论？如果只能靠主观感觉解释，就应该把结论拆小、降级成备注，或改成更可观察的表述。

9. 单句证据必须回到上下文

标签系统里最容易出错的是只看一句话。判断前要补齐：这句话发生在哪个阶段/子场景，是玩家主动说的、回应系统/他人，还是回应事件？它是单次、反复，还是明确表态？上一句或当前事件是什么？没有上下文的证据只能弱支持，不能直接升成稳定偏好。

10. 正向定义必须配套反例和不过度判断规则

只写“什么算”不够，还要写“什么不算”。尤其是游戏、行为、互动类标签，常规动作、被动接受、高压临时反应、ASR 噪音、玩笑/破壁、单次情绪，都要先排除，再判断是否进入稳定画像。

11. 用户反馈优先用于修正边界，而不是只修正文案

当用户觉得一个名字不准、一个例子误判、一个字段重叠时，不要只换词。要回头检查这个槽位回答的问题、证据边界、消费场景和旧结构迁移是否都需要调整。

一句话总结：先问“它回答什么问题”，再判断“它归哪个已有边界”，然后决定“证据怎么抓、反例怎么排除、要不要拆、怎么枚举、旧结构怎么迁移、下游能不能行动”。

## 与用户协作时的需求澄清偏好

1. 先确认边界，不要把“能想到的增强”当成需求

用户对需求范围非常敏感。不要因为某个功能“看起来有用”就主动加入第一版，例如热力图、额外建议结论、轻量版替代 full 版。只有用户明确需要，或它是当前目标的必要路径，才进入执行范围。

2. 区分 hidden reasoning 和 executor-facing spec

讨论过程中可以用旧版参考、历史上下文、推理过程帮助自己理解，但写给执行者的 plan 只保留：要什么、改哪里、怎么改、怎么验收。不要把“我为什么这么想”的长推理塞进执行文档。

3. 用户常通过追问来逼近真实需求

当用户说“再问我 10 个问题”或反复质疑某个口径时，不是在要求机械问答，而是在共同收敛概念边界。此时 agent 应该提出关键澄清问题，并把答案转译成稳定规则，而不是急着落代码。

4. 分清分析类字段和行动类字段

用户会明确区分“用于汇报/分布统计的分析维度”和“用于未来线上 informed decision 的行动证据”。例如年龄、性别、段位、粉丝倾向是后台分析维度，不直接驱动 bot 行为；情绪触发、主动话题、承接、维持、callback 才是行动证据。

5. 对低置信度画像宁可未知，不要猜

用户宁愿看到大量 `未知/未观察`，也不接受从语气、昵称、称呼、撒娇、人设互动、单局输赢里强推年龄、性别、段位或粉丝倾向。未知不是失败，而是严格证据门槛的表现。

6. 不要用降级方案偷换用户目标

当 full 版本打不开时，不能直接把结果降级成轻量版并宣称完成。正确思路是先保留用户目标，再解决性能问题，例如外部化大图、拆资源、懒加载、修 JS 错误。只有用户同意，才可以改变交付内容。

7. 结论必须可验证，不要过早断言

域名、端口、路径、部署状态、页面是否可打开，都要实际验证。不要只凭短域名解析失败就断言“没有”；要确认完整输入，例如 `.woa.com` 后缀、协议是 `http` 还是 `https`、服务目录是否指向当前项目。

8. UI 反馈通常指向信息表达方式，不只是 CSS 微调

用户说“丑”时，往往不是单个颜色或边距问题，而是信息表达模型不对。例如基础画像分布用 pill 像后台筛选器，不像报告；更合适的是复用已有报告里的 chart-card、bar、doughnut、气泡/词云等视觉语言。

一句话总结：先把用户真正要保留的目标守住，再在边界内解决问题；计划写给执行者，判断基于证据，交付以可访问、可验证、符合报告质感为准。

## 判断一个概念/层级是否应该存在

1. 先问问题，不先建结构

任何新字段、新图层、新模块、新结论，先问它回答什么问题。回答不出独立问题，就不应该单独存在。不要因为一个概念听起来合理，就默认它值得成为一层结构。

2. 区分证据、解释、决策、展示

不要把展示层的解释包装成真实推理层。一个信息如果只是为了让读者更容易理解，它属于 presentation；只有它被推理过程真实消费，才是 reasoning layer。

3. 中间层必须有信息增量

一个中间层成立，需要同时满足三个条件：有上游证据来源，有稳定归纳规则，有下游消费方。如果它只是把两个最终结论再包一层名字，或者只是把已有字段换个标题展示，就没有信息增量。

4. 信息流向必须是真实消费关系

图里的箭头不能只是“看起来相关”。箭头意味着下游判断真的使用了上游信息；如果 prompt、代码或实际决策链路没有消费这条信息，就不要把它画成主流程。否则就是 fake flow。

5. 先修自洽，再加需求

修改 plan 时，先检查旧 plan 有没有矛盾、过期说法、重复概念或不可能的执行顺序；修完旧矛盾，再加入新需求；加完后再复查一遍，确认没有残留旧口径。

6. 用户质疑通常是在校准边界

当用户反复问“有没有必要单独一层”“这个流向是不是真的”“是不是 fake”时，不要急着维护原方案。回到：它回答什么问题、来自哪些证据、是否被推理过程消费、删掉后是否损失信息、是否会误导执行者。

7. 不要为了图完整而保留无信息节点

结构图里的每个节点都应该承担独立语义。若某个节点只是把已有结论打包，例如“最终结果”只等于 A+B，那么它更适合作为 column name 或 section title，而不是独立推理节点。

一句话总结：先判断一个东西是否有独立问题、真实来源、稳定归纳和下游消费；没有这四点，就不要把它升格成结构层。
